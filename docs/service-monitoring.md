# Service Delivery Monitoring

The bureau's quarterly service-delivery data collection (accountability, institution building, technology-supported services, service standard), moved from Word templates sent over Telegram/WhatsApp into the system.

Sidebar: **Operations › Service Delivery Monitoring** (`/service-monitoring/...`).

## Why a form builder

The Word templates change from period to period. They are also not tied to one administrative level: a sub-city, a woreda, a bureau or an agency may each report. So nothing about a form lives in code:

- A **form** is data (a schema), built and versioned in the UI.
- A form is **assigned to organization types**. Every active institution of those types is expected to report on it. There is no hard-coded "sub-city / city" level, label or column group anywhere: the consolidated report groups institutions by whatever types the form is assigned to.
- The **fiscal year belongs to the reporting period**, not to the form, so one form serves every year.

## Concepts

| Concept | Table | Notes |
|---|---|---|
| Form version | `service_monitoring_forms` | `code` + `version` is unique. `draft` → `published` → `superseded` → `archived`. Holds the schema (JSON). |
| Assignment | `service_monitoring_form_organization_type` | The organization types that report on a form version. |
| Reporting period | `service_monitoring_periods` | Fiscal year (E.C.) + `first_quarter` / `half_year` / `nine_months` / `annual`; `open` or `closed`. |
| Report | `service_monitoring_submissions` | One per form **code**, period and organization. Pins the exact form version it was filled on. `draft` → `submitted` → `accepted`, or `returned` → `submitted`. Optional stamped copy (PDF/JPG/PNG, ≤ 10 MB, private disk). |

## Schema

`App\Support\ServiceMonitoring\FormSchema` is the single contract; `resources/js/Components/serviceMonitoring/types.ts` mirrors it.

```
{ sections: [ { key, title, blocks: [ block … ] } ] }
```

| Block | Fields | Answer |
|---|---|---|
| `note` | `text` | none (instructions, ማሳሰቢያ) |
| `text` | `label`, `required` | a string |
| `table` | `title`, `description`, `row_mode`, `rows` (fixed), `max_rows` (dynamic), `show_totals`, `column_groups`, `columns` | see row modes |

Row modes:
- `dynamic`: the institution adds rows (people held accountable, digitised services). The answer is a list; blank rows are dropped.
- `fixed`: predefined rows (the action types). The answer is keyed by row key.
- `single`: exactly one row (the institution's own figures).

Column types: `text`, `textarea`, `number` (≥ 0, two decimals), `check` (the "X" mark), `select` (listed options), `sum` (a row total of named number columns).

Column groups put one heading over several consecutive columns, reproducing the two-level headings of the paper forms.

The server recomputes every `sum` column and every total, so a client can never submit a ድምር that disagrees with its own figures. Drafts may be incomplete. Submitting enforces required answers.

Keys are generated by the builder and never typed. Limits: 30 sections, 30 blocks per section, 40 columns, 100 fixed rows, 500 dynamic rows.

## Versions

- Only a **draft** changes. Publishing validates the schema for completeness, requires at least one organization type, and supersedes the previously published version of the same code.
- **New version** copies a version into the next draft (one draft per code).
- **Copy as new form** starts an independent form (new code, v1).
- **Archive** retires a published or superseded version. **Discard** deletes a draft no report uses.

## Reports

- An institution opens a report by choosing an open period, a published form and an institution. Only institutions of the form's organization types, inside the user's organization scope, are offered and accepted. Opening an existing report reopens it.
- The institution saves drafts and submits. A submitted report is locked unless it is returned.
- A reviewer accepts it or returns it with a note. The submitter can never review their own report (maker ≠ checker).
- A closed period freezes its reports.

## Consolidated report

`ServiceMonitoringSummaryService` builds it from submitted (or, optionally, only accepted) reports inside the viewer's scope:

- **Fixed-row tables:** sums per row and column, for each assigned organization type and overall. This replaces the paper form's "ክ/ከተማ | ወረዳ" column groups with whatever types are assigned.
- **Row-entry tables:** every institution's rows, named, with the totals of all rows (up to 2,000 rows listed).
- **Text answers:** listed per institution.
- **Coverage:** institutions expected, reports counted, drafts and returned reports, and up to 100 institutions that have not reported.

Reports filled on an earlier version are read through the selected version's layout, matching cells by key.

## Permissions

| Permission | Duty | Default roles |
|---|---|---|
| `service_monitoring.forms.manage` | Build, version, publish and archive forms | Super/System/City Admin, Public Service Bureau Admin |
| `service_monitoring.periods.manage` | Open and close periods | same |
| `service_monitoring.reports.submit` | Fill and submit an institution's report (in scope) | the above + Organizational Admin |
| `service_monitoring.reports.review` | Accept or return a report (in scope) | Super/System/City Admin, Public Service Bureau Admin |
| `service_monitoring.reports.view` | Read reports and the consolidated report (in scope) | the above + Organizational Admin |

Every report action checks both the permission and the report's institution against `OrganizationScopeService`. Every lifecycle change is written to the audit log (`service_monitoring.*` events).

## Starter form

`database/seeders/data/service-monitoring-forms/service-delivery-quarterly.php` holds the bureau's Word templates, generalised. The institution reports for itself (no sub-city/woreda rows). There is no fiscal year in the text, and the Telegram/WhatsApp step is replaced by the stamped-copy upload.

It is seeded once, as a **draft** with no organization types assigned. An administrator assigns types, adjusts it in the builder and publishes it. A form whose code already exists is never overwritten.
